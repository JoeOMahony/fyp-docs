### Hive-style partitioning strategy

The pattern I came across, and am testing, is the hive-style partitioning strategy used in data lakes, lakehouses, and columnar databases. This is where I would use directory names for partitioning with key-value pairs. The implementation that made sense to me was to use type and time to partition files.

For a rough code example of a parition:

    `f"raw/source={api}/icao={icao_airport_code}/year={now.year}/month={now.month}/day={now.day}/hour={now.hour}`

This does have raise issues though:

- METARs is updated every 30 minues 24/7 at the major Irish airports, so what's the last partition? If it's per-hour, that's only 2 entries per airport. The airport must be in the partition, because that's how it will be queried. The solution probably lies within using time-ranges, but you're still going to have to weigh up the cost of JOINs if a flight is in the zone around a partition. Countering this by having day as the partition means you'll have data you don't need returned from queries.
- A poor partitioning scheme will result in the scattered small files problem.
- Do I want raw data? "Raw" means raw, what use do I have for machine code.
- If I'm using S3, what will be the key of the files? It will need to be unique, probably use a UUID, but what else do I want in it?
