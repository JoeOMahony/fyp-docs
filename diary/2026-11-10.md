### Fixed CloudWatch Alarms
Over the last week, I've received maybe 3 emails a day for failing alarms from CloudWatch, all to do with how I implemented the FlightAware missed run alarm and AWC ingest error alarms. I investigated the logs and made the following fixes:
1. `aeroq-flightaware-ingest-missed-runs` used a sliding window (the default). This had the side effect where at the time the first departures ingest run occured, the number of invocations over that 24-hour sliding window would drop to one. The arrivals run takes place a half an hour later. I changed this to calendar time (midnight to midnight UTC), which should resolve the issue. The side effect is that the check for the alarm is done 20 hours later (~4am runs to midnight check).
2. `aeroq-metar-ingest-errors` was set to alarm on GTE one error within an hour. This was too low for the simple reason that airports, Shannon in particular, seem to fail more in the middle of the night when there aren't any arrivals/departures. METAR has redundancy built in, so the next run should scoop up the missed data anyways. I changed this to GTE 2 runs.
3. `aeroq-isigmet-ingest-errors` had the same problem as METARs, changed to GTE 2 ingest errors in 2 hours.
4. `aeroq-taf-ingest-errors` was fine I believe, but I still standardised it in line with METARs and ISIGMET.
All of the other alarms (4/8) were fine and functioned as intended, so weren't changed.
None of the above alarms had any effect on the data. The FlightAware ingest alarm was solely due to my poor implementation. The AWC ingest errors were triggered by server-side issues, but my alarms were too strict given the built in redundancy.
